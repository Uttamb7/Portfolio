The challenge

Nimbus models a checkout path that crosses identity, order orchestration, inventory, payment, notification, and analytics boundaries. A failure can be healthy at the process level while still breaking the customer path.

The design goal was not another dashboard. It was a system that could derive relationships from real traffic and connect symptoms to the services they affect.

System design

  • Observed topology: outbound HTTP calls report status and duration, so dependency edges are measured rather than hard-coded.
  • Operational model: the engine calculates request rate, error rate, p95 latency, availability, SLO compliance, and error budget.
  • Incident context: repeated threshold violations create one active incident and topology traversal identifies affected services.
  • Guardrails: bearer identity, role-based actions, query limits, rate limits, and an immutable audit stream protect operational mutations.

Evidence

Every pull request runs dependency auditing, coverage thresholds, Compose validation, and a distributed smoke test. The smoke test starts the full workload, performs a checkout, and verifies that Nimbus observed the expected dependency edges.

Failure scenarios can inject bounded status and latency faults, record the action, show incident impact, and restore the service without restarting the environment.

Honest limits

Nimbus runs locally and does not claim AWS deployment. Event transport is currently HTTP, retries are held in memory, and delivery is at-least-once. Those constraints are documented because reliability work is only useful when its boundaries are explicit.
